# נוהל תגובה ודיווח על אירוע אבטחת מידע
# Breach Notification Runbook

---

> **סיווג:** פנימי — סודי — להפצה מוגבלת  
> **מערכת:** FitGrade  
> **גרסת מסמך:** 1.0  
> **תאריך:** מאי 2026  
> **בעל תפקיד:** ממונה הגנת פרטיות (DPO)  
> **בסיס חוקי:** תיקון 13 לחוק הגנת הפרטיות, התשמ"א-1981 (בתוקף מ-14 באוגוסט 2025)

---

## פרק א׳: הגדרות

**"אירוע אבטחת מידע"** — כל גישה, שימוש, חשיפה, שינוי, מחיקה או אובדן של מידע אישי שלא הורשו, בין אם בכוונה תחילה ובין אם בשוגג.

**"אירוע חמור" (Reportable Breach)** — אירוע העומד בכל אחד מהתנאים הבאים, המחייב דיווח לרשות להגנת הפרטיות (PPA) תוך 72 שעות:

| קריטריון | דוגמאות מ-FitGrade |
|---------|-----------------|
| חשיפת מידע מזהה של יותר מ-100 נושאי מידע | דליפת טבלת `Student` מהמסד |
| חשיפת נתונים רגישים (ת.ז., מ.ל.) בכל כמות | גישה לא מורשית לעמודת `nationalId` |
| פגיעה בנתוני קטינים | כל דליפה של רשומות תלמידים |
| פגיעה בזמינות ממושכת (>24 שעות) | מחיקת מסד נתונים; מתקפת כופרה |
| גישה פנימית לא מורשית | עובד שניגש לנתוני כיתות שאינן שלו |

**"צוות תגובה לאירוע" (IRT)** — הרכב קבוע:

| תפקיד | אחריות |
|-------|--------|
| **ממונה הגנת פרטיות (DPO)** | מוביל התגובה; אחראי על הדיווח לרשות |
| **מנהל טכנולוגיות (CTO/Lead Dev)** | בלימה טכנית, חקירה, תיקון |
| **יועץ משפטי** | ייעוץ משפטי; ניסוח הודעות |
| **מנהל כללי** | החלטות עסקיות; תקשורת חיצונית |
| **ספק אירוח** | סיוע טכני אם הפגיעה בשכבת התשתית |

## פרק ב׳: ציר הזמן הקריטי

```
┌─────────────────────────────────────────────────────────────────┐
│                    ציר הזמן — 72 שעות                           │
├──────────┬──────────────────────────────────────────────────────┤
│ שעה 0    │ גילוי האירוע — פתיחת יומן אירוע (נספח א׳)           │
│ שעה 0–1  │ בלימה ראשונית + הודעה לממונה הגנת פרטיות            │
│ שעה 1–4  │ הערכת חומרה — האם האירוע "חמור"?                    │
│ שעה 4–12 │ כינוס צוות IRT + אבטחת ראיות דיגיטליות             │
│ שעה 12–48│ חקירה מלאה + הכנת דיווח לרשות                       │
│ שעה 48–72│ ← מועד אחרון לדיווח לרשות להגנת הפרטיות (PPA)       │
│ שעה 72+  │ הודעה לנושאי מידע + תיקון מלא + תחקיר               │
└──────────┴──────────────────────────────────────────────────────┘
```

> **אזהרה:** שעת ה"גילוי" מתחילה ברגע שהארגון **ידע או היה עליו לדעת** על האירוע — לא ברגע האישור הרשמי.

## פרק ג׳: נוהל שלב-אחר-שלב

### שלב 1 — זיהוי וגילוי (שעה 0)

**מקורות גילוי אפשריים:**
- התראה מיומן הביקורת (`AuditLog`) — גישה חריגה לשדה `nationalId` או פעולות מרובות מ-actorId יחיד
- התראה ממערכת הניטור (RUM) — שגיאות 4xx/5xx חריגות בנפח גבוה
- דיווח מורה/תלמיד על פעילות חשודה בחשבון
- גילוי פנימי על ידי מפתח / מנהל מערכת
- דיווח חיצוני (חוקר אבטחה, גורם שלישי, CERT-IL)
- כשל בבדיקת שלמות גיבוי

**פעולות מיידיות (תוך 30 דקות מהגילוי):**

1. תעד את **שעת הגילוי המדויקת** ב-יומן האירוע (נספח א׳)
2. הודע ל-DPO — **בכל שעה, כולל לילה וסופי שבוע**
3. **אל תמחק** שום קובץ log, גיבוי, או רשומת מסד נתונים
4. **אל תודיע** לגורמים חיצוניים עד לאישור ה-DPO
5. צלם מסך / שמור את ההתראה שגרמה לגילוי

---

### שלב 2 — בלימה ראשונית (שעה 0–1)

| פעולה | אחראי | כלי ב-FitGrade |
|-------|-------|---------------|
| נתק גישה של ה-IP / חשבון החשוד | CTO | Firewall / הגדרות שרת |
| בטל את כל טוקני ה-JWT של חשבונות מושפעים | CTO | טבלת `RefreshTokenBlacklist` (הוסף `jti` לרשימת ביטול) |
| הפעל מצב קריאה-בלבד אם נדרש | CTO | הגדרות שרת |
| שמור עותק בלתי-ניתן-לשינוי של ה-logs | CTO | `AuditLog` table dump + server access logs |
| תעד את כל הפעולות ב-יומן האירוע | DPO | נספח א׳ |

---

### שלב 3 — הערכת חומרה (שעה 1–4)

ה-DPO מבצע הערכה לפי שאלות הסף הבאות:

```
שאלה 1: האם נחשפה ת.ז. גולמית של תלמידים?        כן → חמור ⚠️
שאלה 2: האם נחשפו נתוני קטינים בכל צורה?          כן → חמור ⚠️
שאלה 3: האם נחשפו יותר מ-100 רשומות?             כן → חמור ⚠️
שאלה 4: האם קיים סיכון ממשי לנזק לנושאי מידע?     כן → שקול דיווח
שאלה 5: האם האירוע הוכל לחלוטין וללא נזק?          כן → תיעוד פנימי בלבד
```

**אם תשובה אחת לפחות היא "כן" לשאלות 1–3 → עבור מיד לשלב 5 (דיווח לרשות).**

---

### שלב 4 — חקירה מלאה (שעה 4–48)

**שאלות שיש לענות עליהן:**

**מה נחשף?**
- בדוק טבלאות: `Student`, `TestResult`, `AttendanceRecord`, `TalmidautRecord`, `AuditLog`
- האם נחשף שדה `nationalId` גולמי (לא מסווג)?
- האם נחשפו `passwordHash`-ים?

**מתי החל האירוע?**
- חפש ב-`AuditLog` את הפעולות הראשונות החשודות לפי `createdAt`
- בדוק server access logs לגישות לא מורשות

**מי מעורב?**
- בדוק `AuditLog.actorId` לזיהוי חשבונות
- בדוק כתובות IP מה-access logs

**כיצד בוצע האירוע?**
- גישה לא מורשית לחשבון מורה (credential stuffing / phishing)?
- פגיעות API (authorization bypass, IDOR)?
- גישה ישירה למסד נתונים?
- אירוע פנימי?

**כמה נושאי מידע מושפעים?**
- פרט לפי: כיתות (`classId`), תלמידים (`studentId`), מורים

**תיעוד נדרש לדוח החקירה:**
- [ ] רשימת משתמשים מושפעים (classId, studentId)
- [ ] טווח הזמן המדויק של החשיפה
- [ ] סוגי הנתונים שנחשפו
- [ ] האם הנתונים הועברו לגורמים חיצוניים?
- [ ] צילומי מסך / log excerpts כראיות

### שלב 5 — דיווח לרשות להגנת הפרטיות (תוך 72 שעות)

**אתר הדיווח:** [www.gov.il/he/departments/the_privacy_protection_authority](https://www.gov.il/he/departments/the_privacy_protection_authority)  
**טלפון:** 02-5765000  
**דוא"ל:** ppa@justice.gov.il

**מידע נדרש לטופס הדיווח:**

| שדה | מה למלא |
|-----|---------|
| שם בעל המאגר | FitGrade |
| פרטי הממונה (DPO) | [שם, טלפון, דוא"ל] |
| תיאור האירוע | מה, מתי, איך |
| קטגוריות נושאי מידע | מורים / תלמידים / שניהם |
| כמות נושאי מידע מושפעים | מספר מדויק ככל האפשר |
| קטגוריות נתונים שנחשפו | ת.ז. / שם / ציונים / נוכחות |
| ההשלכות הצפויות | סיכון לגניבת זהות / הונאה / פגיעה בפרטיות |
| אמצעי הבלימה שננקטו | רשימת הפעולות משלב 2 |
| האם הודעה תשלח לנושאי מידע | כן / לא (עם הסבר) |

> **אם לא ניתן לדווח תוך 72 שעות** — יש לדווח בהקדם האפשרי ולציין את הסיבה לאיחור בטופס.

---

### שלב 6 — הודעה לנושאי מידע (שעה 72+)

**מי מקבל הודעה:**
- מנהלי בתי הספר המושפעים (דרך כתובת הדוא"ל של המורה הרשום ב-Google OAuth)
- נושאי מידע הנמצאים בסיכון ממשי לנזק ישיר

**אמצעי הודעה:**
- דוא"ל לכתובת המורה הרשומה
- במקרה חמור — הודעה בכתב רשמית לבית הספר

**לשימוש:** תבנית ההודעה בפרק ד׳ להלן.

---

### שלב 7 — תיקון ושיקום (שבוע 1–2)

1. טפל בפגיעות שנוצלה (Patch / Configuration fix)
2. אפס סיסמאות וטוקני גישה של כל החשבונות המושפעים
3. הגבר ניטור ב-`AuditLog` לפעילות חריגה
4. בצע סריקת אבטחה ממוקדת באזור המושפע
5. עדכן `pnpm audit` ובדוק אם יש תלויות פגיעות חדשות
6. הכן **דוח פנימי מלא (Post-Incident Report)** בתוך 30 יום

---

### שלב 8 — תחקיר ולמידה (תוך 30 יום)

ה-DPO מכנס ישיבת תחקיר (Tabletop Review) עם צוות ה-IRT:

- מה עבד טוב בתגובה?
- מה ניתן לשפר בנוהל?
- אילו שינויים טכניים נדרשים?
- האם יש צורך לעדכן את מסמך ה-ROPA?
- האם יש צורך להדריך מחדש את הצוות?
